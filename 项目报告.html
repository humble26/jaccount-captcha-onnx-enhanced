1. 项目概述

要解决的问题

上海交大 jAccount 登录页每次登录都要人工辨认验证码。用户原先安装的 Greasyfork 脚本 「jAccount 验证码识别 - Tesseract 版 v3.1.0」存在致命缺陷：脚本里已经写好了 ResNet ONNX 识别函数，却从未被调用——recognize() 只调 recognizeWithTesseract()， 准确率 99% 的模型是一段死代码。于是用户实际跑的是 Tesseract 原图直喂路径，实测仅 74.2%。

做了什么

  • 接上被闲置的 ResNet ONNX 模型，修正后处理（27 类 + blank 跳过判定 4 位码）。
  • 修正二值化阈值方向（>= 156，前景为 1）与灰度取整（Math.round）。
  • 把 CDN 换成国内可达的多源回退，并解决 UMD 全局污染导致的加载失败。
  • 新增「低置信自动换图重试」：模型没把握时自动换一张重来，而不是提交一个可能错的答案。
  • 提供两种发行形态：Violentmonkey 油猴脚本，以及无需任何脚本管理器的 MV3 浏览器扩展（全离线）。

模型

项值

两种发行形态

① 油猴脚本（Violentmonkey / Tampermonkey）

  • 单文件 jaccount-captcha-onnx-enhanced.user.js（87.3 KB）
  • @run-at document-start，下载与页面解析并行
  • ORT 与模型用 Promise.all 并行下载，三级 CDN 回退
  • 保留 Tesseract 兜底（模型需联网，兜底仍有意义）
  • UMD 受控作用域加载：把 define/exports/module 遮蔽为 undefined， 强制 UMD 走 e.ort = t()（详见事故复盘 9.3）

② MV3 浏览器扩展（无需脚本管理器）

  • content.js = ORT UMD（剥离 sourceMap）+ 本项目 app.js，单文件约 579 KB
  • wasm（10.41 MB）与模型随包分发，经 fetch(chrome.runtime.getURL(...)) 读成 ArrayBuffer
  • env.wasm.wasmBinary 直接喂字节 —— 全程零网络请求
  • 因此去掉了 Tesseract 兜底：它的存在理由（模型需联网）已消失
  • content script 里 document.currentScript 为 null，ORT 的路径推导走不通， 所以 wasmBinary 不是优化而是必需

低置信换图重试（v4.5.x 核心机制）

模型对"这一张能不能信"会给出一个最低字符置信度。实测发现：阈值取 0.999 时，84.5% 的图 一次就能给出 100% 正确的答案，剩下 15.5% 不猜，改为自动点「换一张」重新识别（最多 3 次）。 这样设计的原因是错误样本的置信度（84.39%~99.58%）与正确样本完全重叠，靠阈值无法直接筛错， 但"换一张再来"能绕开它。

阈值自动化率自动部分准确率错误拦截说明
95.0%99.1%98.17%1/5几乎不拦截，等于没保护
99.0%96.8%99.06%3/5—
99.5%95.9%99.53%4/5—
99.9%84.5%100.00%5/5选定 自动部分绝不提交错误答案
历史教训：这个阈值在项目早期是 0.60，而全部 5 个错误样本的最低置信 都在 84% 以上——0.60 永远够不到，该功能形同虚设好几个版本而无人察觉。单看代码发现不了， 是靠标注数据的实测分布才定位的。

关键实现约束（踩过坑后固化的规则）

  • suppressObserver() 必须在 btn.click() 之前调用：站点同步改 src 时，放后面闸门等于白设。
  • 换图后必须确认 src 真的变了 才去 decode：img.decode() 在「src 未变且旧图已解码」时会立即兑现，导致在旧图上识别。
  • decode() 抛 AbortError 的含义是「被更新的 src 取消」＝新图还在路上，不是已就绪。
  • 换图之后此前所有识别结果立即作废——置信度是"这一张能不能信"，不能跨图片比较。
  • 提示元素一律插入文档流内（insertBefore(el, img.nextSibling)），禁止 position 定位。

两个被推翻的中间结论（靠扩大样本 + 留出集救回来的）： ① 20 张时看到的「Tesseract 调优 80%→85%」在 120 张上完全打平，是小样本噪声，真实收益只有速度； ② 「27 类 + blank 跳过」是确定性缺陷修复（原版会把 kwwkc 误截成 kwwk）， 方向正确但不能当作可测量的准确率增益来汇报。

错误分布（本项目主路径 5 个错例）

  • 100% 集中在第 4 个字符槽：第 1/2/3 位 220 张零错，第 5 位 107 张零错。
  • 第 4 个输出头最低置信 84.39%，其余头 96.98%~99.38%——系统性最弱。
  • 错误全是视觉近邻混淆：x→o、c→o、y→u、w→g、g→z。
  • 987 个真值字符中 982 个 top1、3 个 top2、2 个 top3，从未掉出 top-3。
  • 第 4 位笔画密度：错误样本 14.0% vs 正确样本 16.5%——排除了「字太糊」这一解释。

4. 模型天花板与架构评估

结论：97.7% 已接近该模型 + 该数据的判别极限，靶点唯一（第 4 位）。以下是实测否证过的路径， 记录在此以免重复劳动。

已否证（勿重试）

方案实测结果
TTA（平移 ±1px 后 logits 平均，1×3 / 3×3）base 215 → 214，改进 0 退化 1，负收益
11 种预处理变体（阈值 130~200、列平移 ±1、行缩放 0.97/1.03）+ 逐位投票净收益恒为 0
二值化阈值扫描 145~175全在 116/120 的平台上，156 已在最优区
直接喂灰度（不二值化）0/220，模型要求硬 0/1 输入
ORT 四个优化等级（DISABLE_ALL / BASIC / EXTENDED / ALL）预测完全一致，只影响启动耗时
在冻结的 64 维特征上重训分类头（加宽/加深）99.60% → 57.89%（−41.71 pp），所有位置 p=0.000
Tesseract PSM 8所有图像组合下掉到 35~60%，是准确率杀手
「换头」是常见误区：原生头与 backbone 是端到端联合优化的。冻结特征后换头， 只是在已经「过度专属」的特征空间里拟合 220 个样本。重构必须端到端重训，不能只换头。

五个架构假设，实测否证 4 个

假设判定依据
全局池化丢位置信息否证抹掉第 4 槽时第 4 头输出改变 192/220；只保留第 4 槽时准确率降到 80.5%（依赖上下文）
二值化丢灰度反向否证灰度可分率 43.64% < 二值 55.91%（5 个位置全更差）——灰度渐变是干扰而非信号
64 维特征太窄否证跨集迁移仅 32~74%（集内 99~100%），特征过度专属，扩容量会加剧过拟合
输出头太浅部分成立2 层 MLP 比单层线性头 +3~8 pp，趋势支持但幅度小
需要序列建模（CTC）否证长度判定零错误（4 字符码 blank 113/113 全对）

图像物理限制

  • 画布 110×40，字形高 16.9 px、宽 86.2 px，单字符约 19.2×17 px。
  • 白底占 93.08%，笔画仅 6.92%（约 304 px/张）；48.6% 的笔画只有 1~2 px 宽。
  • 因此改架构的理论天花板约 98.5%~99.0%，且需重采集 + 重训 + 全链路回归。

推荐路线（按性价比排序）

  1. 零风险现成解（已落地）：低置信换图重试，阈值 0.999 → 84.5% 全自动且 100% 正确。
  2. 定向增数据 + 端到端重训：8 个高危字符 c,g,o,u,w,x,y,z 在第 4 位各达 60 例， 需补约 171 个字符位（约 38 张验证码即可覆盖，成本比想象低）；2000 张目标配额为基础每字符 346 次 + 高危字符额外 173。
  3. 加深输出头（2 层 MLP）+ 增广 / 正则。
  4. 不要做：扩宽 64 维、改灰度输入、CTC 序列解码、加回空间结构。

工具已就位：analysis/targeted_sampling.py（定向采样配额表）与 analysis/train_refactor.py（extract / train / eval 三个子命令，已跑通）。

测试也会出错——这是本项目最贵的一条经验。 在 v4.5.1 复审时，6 条既有测试断言的正是被修掉的错误行为（例如断言「换图失败后保留首次结果」、 断言「src 不变时 decode 也要立即兑现」）。它们"通过"只是在给错误行为背书。 另有三处测试桩从不真的改 src，模拟的其实是"换图没生效"这种异常场景。 凡"修了正确行为后既有测试变红"，先怀疑测试，但必须逐条确认，不能批量改预期。

安装要点

  1. 油猴版：Violentmonkey 控制台 → + → 「从文件安装」。
  2. 必须先禁用/删除旧脚本（jAccount 验证码识别 - Tesseract 版）— 两者 @match 相同，同时启用会互相覆盖输入框。
  3. 扩展版：Chrome/Edge 扩展页开启「开发者模式」→「加载已解压的扩展程序」→ 选解压后的 jaccount-captcha-extension 目录。

排查开关

  • 油猴版：把脚本里 CFG.debug 改为 true，控制台按 [jAccount] 过滤。
  • 扩展版：登录页控制台执行 localStorage.jaccountCaptchaDebug = '1' 后刷新（改一个标志就要重新加载扩展太麻烦）。
  • 失败时页面会显示带版本号 + 失败环节 + 完整错误的提示条，把这段文字发出来即可定位—— 4.4.3 的横幅正是靠它一次就抓到了真正的根因。

8. 修改记录（17 版时间线）

v4.0.0 · 接上被闲置的 ResNet 模型

第一轮 · 问题发现与重构
  • 调用真正的 recognizeWithONNX()（原为死代码）。
  • 后处理改 27 类 + blank@26 跳过判定 4 位码（原版对 5 头一律取前 26 类，永远选不出 blank）。
  • 二值化阈值 > 156 → >= 156（官方 LUT 是 [0]*156 + [1]*100）。
  • 模型 URL 从 raw.githubusercontent.com 换成多源 CDN。

v4.1.0 · 代码审查修 8 处

第二轮 · 120 张样本复测后
  • 换图可能漏识别（最严重）：用 src + 宽高 做指纹去重，src 变更时尺寸还是旧值 → 新验证码被跳过。改为 load/decode 事件驱动 + 80 ms 防抖。
  • 可能读到旧帧：img.complete 在 src 刚改写时仍可能为 true → 改用 await img.decode()。
  • 吞掉 ORT 的 [E:onnxruntime 错误日志 → 只静音 W 级。
  • ONNX 单次失败即永久降级 → 改为连续 2 次才放弃。

9. 重大事故复盘

9.1 · 4.4.0 重构时删掉了核心语句

现象：用户装 4.4.0 后所有识别全部失败。根因：重写 loadScript 时漏掉 s.src = url; ——创建 script、挂 onload/onerror、appendChild，但从未给它地址。onload 永不触发 → 每个源走 15 s 超时 → 全失败。

为什么没测出来：抽出 loadScript 跑场景测试时，括号平衡被新代码干扰而报错， 我没有坚持把它查到底就转去跑别的测试了。如果当时查到底，这个 bug 在上线前就会暴露。

9.2 · 四轮"猜 bug"全部落空

4.4.1、4.4.2、4.4.3 连续三轮，用户反馈始终只有一句「识别失败」。所有失败在界面上长得一模一样： ORT 没加载上、模型下不下来、wasm 起不来、Tesseract 拉不到——都是同一句话。 期间逐一实测排除了：jAccount 页面 CSP（不成立，响应头无 script-src 限制）、CDN 可达性（四个资源全 200 + MIME 正确）、 ORT 缺 glue 文件（不成立）、Node 报 b.normalize is not a function（是 Node 缺 fake-path 的环境问题， 浏览器不出现，不能当证据）。

9.3 · 沙箱全绿而真实环境失败：UMD 全局污染

转折点来自 4.4.3 的横幅：[加载 ORT] 脚本已加载但 window.ort 未出现。 一句话锁定了 UMD 四路分支问题。此前 5 轮全部测不出来的原因：沙箱环境是干净的，没有 define/exports，永远走第四分支成功——测试环境与真实环境存在一个从未被识别的差异维度。

正确做法（已被验证有效）：当用户只能给出 1 bit 反馈（"失败/成功"）而问题有 N 种成因时， 优先级最高的工作不是修 bug，而是把 N 种成因变成 N 种可区分的用户可见信号。 观测一旦到位，修复往往只是一行代码的事——本项目正是如此（横幅上线后一次就定位了拖了四轮的根因）。

10. 经验教训清单

工程方法

  1. "上一轮修好了"不等于"修对了"。4.5.0 解决了"能不能跑"（不再干等 1200 ms）， 却引入了"跑得快但跑错"（在旧图上识别）。修完要问一句：修的是症状还是语义？
  2. 重构和修 bug 是两件事。重构时删掉的每一行都要有明确的去处，改完必须逐行核对新旧版本的功能等价性。
  3. 修 bug 要同时测"修复方向的反面"。4.3.0 修对了 A 面（换图后不丢答案）却漏了 B 面（空值 + 焦点在内被冲掉）。 判定表要按二维穷举，不能只测想到的那几行。
  4. 自触发反馈回路必须显式建模。任何 A→B→A 的环路都要问"现有幂等护栏在这个环路上还成立吗"—— runToken 和防抖都是为单次触发设计的，遇到自我激励循环同时失效。
  5. 跨尺度比较前先确认单位。曾拿自己算的 softmax 概率去对照脚本里原始 logit 的阈值， 得出"该阈值永不生效"的错误结论。断言"某阈值不生效"前，先确认那个变量到底是什么。

实验与数据

  1. 20 张样本不足以区分 80% 与 85%（单张 5%）。验证类实验至少要 100 张量级， 且要用配对检验（McNemar）而不是比较两个独立准确率。本项目靠留出集救回了两次误判（TTA、Tesseract 调优）。
  2. 改参数前先核对原阈值是否真的生效。lowConfidence: 0.60 让"低置信标注"形同虚设好几个版本， 单看代码完全发现不了。
  3. 先验证预处理方向再分析。>=156 与 <156 的方向错误曾让一整轮架构分析作废； 做掩码类分析前先打印像素直方图并可视化。
  4. "在冻结特征上换分类头"是误区。端到端联合优化的头无法被离线重训复现（实测 −41.71 pp）。

测试

  1. 测试会把当时的理解固化成预期。为"decode 立即兑现"写的 3 条回归锁，成功阻止了后来的正确修复。 凡"修了正确行为后既有测试变红"，先怀疑测试，但必须逐条确认。
  2. 被测代码必须从真实源码抽取（大括号配平 + new Function）， 手抄副本会静默过时。带 ++ 赋值的模块级变量要用持有者对象桥接（RT.v），getter 写不回。
  3. 测试桩的假数据会制造假失败（网络桩返回全零 ArrayBuffer → ORT 源码变成 1 MB 的 \0）。 测试跑到一半崩溃也会被误读成通过。
  4. 检查脚本里禁止出现版本字面量。硬编码版本号在本项目出现过三次，每次升版都制造假失败。
  5. 沙箱全绿而真实环境失败时，不要只怀疑代码逻辑，要逐一列举"沙箱与真实环境的差异维度"（全局变量、CSP、 时机、网络…），然后为每个维度专门构造测试。
